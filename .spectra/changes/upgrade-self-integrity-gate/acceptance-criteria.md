## Problem (measured on `main` @ `933f36b`, VERSION 2.20.0)

| Where the expected metadata could live | Can it hold the target's own values? |
|---|---|
| installed nexus roster (`$ROSTER_FILE`, what the code reads today) | **No** — it is the *previous* release's roster |
| the target tag's own tree (`$NEXUS_NEW` at `vX.Y.Z`) | **No** — measured: `v2.20.0`'s roster returns `ABSENT` for `2.20.0` |
| upstream default branch | **Yes** — measured: `commit 2cd2d098… tree 85a3c084… archive_sha256 2bcafa31…`, all three matching a fresh clone of the tag |

Every forward upgrade therefore takes `return 0` at `cli/src/lib.sh:1009-1012`.
`upgrade_self.sh:285-299` refuses on rc 2 and rc 3; neither is reachable when
the metadata is absent. Live on 2.14.1 → 2.20.0: exit 0, nothing checked.

The sibling `else` branch (`upgrade_self.sh:299-301`) is a second live instance:
measured on the fixture, `upgrade self --ref master --force` exits **0** after
printing `Non-tag ref 'master': commit SHA verified, tree/archive checks
skipped.` — a claim of verification on a path where nothing is verified.

**AC-13 is load-bearing**, as in every change in this family: a test written
alongside the code it checks passes trivially. The rows that matter are the
ones that would silently restore the reported behaviour — the `main` hardcode
(correct in production, dead in the harness), a `--allow-unverified` wide
enough to swallow a mismatch, and placeholder-dominant selection.

**AC-1 + AC-2 are a pair.** Neither alone is sufficient: AC-2 without AC-1
proves only that a happy path is green, and AC-1 without AC-2 cannot
distinguish "the gate caught the tamper" from "the gate refuses everything."

**Which criteria can fail against pre-fix code** — stated explicitly, because
a criterion that passes both before and after is a regression guard and must
not be sold as evidence of the fix: **AC-1, AC-2, AC-3, AC-16, AC-17, AC-19, AC-20** fail
pre-fix. AC-10, AC-11 and AC-15 do not — AC-15's three surfaces already
agree on `933f36b`; it exists to stop them diverging when the new flag lands.

**Which criteria fail against the CURRENT implementation** — the round-2
additions, each measured against the shipped code rather than argued:
**AC-21, AC-22, AC-23, AC-25** fail today, and **AC-24** fails both pre-fix and
today. They are not regression guards and must not be reported as green until
the code moves. **Revision 1.5.0 adds two more, and the measurement is
dated because the tree has moved:** **AC-26** and **AC-27** were measured against the
working tree *as it stands on 2026-08-10*, which already carries the 1.4.0
implementation work — they fail against that, not merely against `933f36b`.
AC-26 was reproduced end to end (a reachable upstream reported as unreachable);
AC-27 by forcing an out-of-contract return code (`strict`, no metadata, exit **0**,
`(integrity: verified)`). AC-21 in particular is the row that makes the MONOTONE /
fail-closed invariant true rather than aspirational: **as shipped, one local
file write containing no hashes at all turns a `strict` refusal into
`✓ (integrity: verified:local-only)`, exit 0.**

## Anti-scope

- **The placeholder sentinel keeps its skip semantics.** It is a separate,
  intentional bootstrap path per the issue (a placeholder has appeared in a
  nexus release block exactly once, the v1.0.0 bootstrap, filled shortly
  after). It is made *distinguishable* from a verification (AC-9), not
  repurposed. It is safe **because the severity rule prevents it from masking
  another source's `absent`** (AC-16) — not because an actor who can write a
  roster can also forge hashes, which holds only for origin control and not for
  local-file write.
- **The integrity source is not configurable.** No environment variable
  selects the ref the expected metadata is read from; it is `origin HEAD`.
- No change to the per-Eidolon member integrity path (`verify.sh`,
  `doctor.sh`, `release_metadata_for`, `release_integrity_status`,
  `_verify_release_integrity_internal`), to the release workflow ordering, or
  to any roster data.
- No change to `nexus_refresh`'s own contract, and no call to it added on the
  upgrade path.
- No new exit code: `5` (INTEGRITY_ERROR) covers every refusal.
- **`--check` mode is not covered.** It never clones, so it has no payload to
  verify. A distinct gap, recorded rather than closed.
- **`upgrade_self.bats` S6 is not repaired, and neither is the self-inflicted
  dirty state behind it.** Measured: without `--force`, `upgrade self` exits 1
  at the dirty-tree guard on a file it wrote itself — `nexus_ensure_roster_ref`
  (`upgrade_self.sh:84-86`) creates `$NEXUS/.gitignore`, which is untracked, and
  the guard at line 180 fires on it. The copied CLI scripts are byte-identical
  and are not the cause. S6's missing exit-5 assertion is added as AC-11 rather
  than by editing a test AC-10 requires to stay passing.
  **`docs/cli-reference.md:31` already documents this failure as fixed** — "Without this heal, a freshly-backfilled `.roster_ref` caused `eidolons upgrade
  self`'s dirty-tree check to refuse the upgrade until `--force` was passed" — when the heal is itself what leaves the tree dirty, by writing an untracked
  `.gitignore`. A documented fix that does not fix it is worse than an
  undocumented bug: it retires the search. Recorded here, not repaired.
- **The non-tag outcome (`skipped:non-tag`) proceeds even under `strict`.**
  Refusing it would break the documented `--ref <branch>` workflow. The outcome
  makes it visible; making it a refusal is a separate decision. `skipped:non-tag`
  is this record's **label** for that policy row — what the user sees on the
  summary line is the display string `UNVERIFIED - non-tag ref`, and that is
  what AC-17 asserts.
- **This does not defend against a compromised origin.** Both sources are
  served by the same remote. It defends against drift, corruption, a moved tag,
  and a local-file downgrade. Stated rather than claimed away. **The local-file
  downgrade claim is only true once AC-21 and AC-22 land** — as shipped, a
  local write of `{tag, released_at}` produces `verified:local-only`, exit 0.
- **The placeholder row is unreachable on a forward upgrade — recorded, not
  re-decided.** The installed roster is always `absent` for a version it has
  never seen, and `absent > placeholder`, so a genuine bootstrap-window release
  refuses under `strict` and reports `(absent)`. AC-9 and AC-9b reach the
  placeholder row only by hand-seeding a placeholder into **both** sources. The
  severity rule (critic B-1) and the OQ-2 ruling (keep the skip) were each
  correct in isolation and jointly nullify the case OQ-2 was decided for.
  **OQ-2 is not re-decided here**; the interaction is recorded so the next
  reader does not mistake that row for live behaviour. AC-21/AC-22 do not
  change it — they add no-evidence classifications, which the same rule still
  dominates.
- **AC-23's letter is narrower than its purpose, in three measured ways —
  recorded, none of them fixed here.**
  **(a) A duplicate YAML key silently flips enforcement.** Measured: a roster
  whose text visibly reads `enforcement: strict` but carries a second
  `integrity:` block resolves to **`warn`**. mikefarah `yq` emits *both*
  duplicates and `jq` takes last-wins; the `python3` fallback's
  `yaml.safe_load` takes last-wins at parse time — so **both backends agree on
  `warn`**, and they differ only in where the de-duplication happens. `yq eval .`
  and `jq empty` — exactly what `make schema` runs — both exit **0**. AC-23
  clause (ii) checks that the roster *parses*, and a duplicate-key roster parses
  fine, so this defeats `_upgrade_self_enforcement_mode`'s stated purpose without
  violating its letter. **Out of scope, with the reasoning recorded rather than
  the conclusion:** the right instrument is a duplicate-key check in roster CI,
  not in one call site's enforcement read — a fix here would guard a single
  reader while every other reader of the same file (`verify.sh`, `doctor.sh`,
  `roster_get`, `make schema` itself) keeps taking last-wins, which is a fix that
  looks like one and closes nothing. Filed separately.
  **(b) `tr -d '[:space:]'` strips *interior* whitespace**, so `'wa rn'`
  normalises to `warn` where clause (i)'s "trim surrounding whitespace" would
  refuse (measured). Degenerate — it needs environment control, which is already
  a stronger position than the value it forges — and the outcome is identical to
  pre-fix, where the verbatim `wa rn` also failed the `== "strict"` compare and
  proceeded. No worse than pre-fix, and recorded so it is not mistaken for a hole
  the criterion claimed to close.
  **(c) A 0-byte roster parses to `null`**, so clause (ii)'s parse check passes
  (`yq -o=json` on an empty file prints `null`, exit 0) and
  `.integrity.enforcement // "warn"` yields **`warn`** under both backends.
  Within the criterion's letter.
- **Two follow-ups are filed, deliberately without criteria.** (1) Requiring
  `commit`/`tree`/`archive_sha256` in `schemas/roster.schema.json` — irrelevant
  to the AC-21 local-write attack, because nothing validates the **installed**
  roster against the schema at read time; a read-time classifier fix (AC-21) is
  the load-bearing one and a schema change would look like a fix while closing
  nothing. (2) `integrity_enforcement_mode`'s fail-open behaviour for
  `verify.sh` and `doctor.sh` — the same helper, the same fail-open, on the
  frozen member-integrity path. AC-23 fixes the **upgrade call site only**, and
  the asymmetry is deliberate and recorded rather than silently created.
