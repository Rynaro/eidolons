**Closed — FIXED in v2.1.0.**

**This was live at default deployment, and the issue's "no error, no log line, no explain
anomaly" description was accurate.** `config.py` defaults `recall_active_only=True` and both
entrypoints (`server.py`, `__main__.py`) pass it through; the `False` on the `Aetheryte`
constructor binds only for direct construction in evals and tests. So deprecated rows really
did consume fetch slots and starve active hits in shipped deployments, silently.

That distinction mattered: a fixture copied from the eval template would have pinned the flag
`False`, where `_is_active` returns `True` unconditionally — and tested dead code while
appearing to pass. The shipped fixture pins `recall_active_only=True` and asserts it by reading
the flag back **off the `Aetheryte` instance**, never off the kwargs dict it just wrote.

**The fix**, caller-side in `retrieve.py` only: count candidates failing `_is_active`; if any
are inactive AND the fetch was censored, widen **each individually censored-and-dirty fetch**
at most once, merge preserving BM25 order, dedupe, and recompute the censoring signal against
the fetch actually performed.

**Widening only the global head was rejected on measurement.** On the strict-subset path the
head is the global call, which K-N12's own premise says is dominated by excluded layers — so
head-only is near-inert there. Disabling only the backstop's widen turns
`test_subset_status_topup_recovers_active_hits` RED with the target unrecoverable and
`widened_fetches == []`. Head-only would have shipped `sparse_topup.fired: true` with recovery
structurally absent.

**The counter is honest.** `explain.fusion.sparse_topup {fired, k_initial, k_final,
n_inactive_observed}` is derived from the fetch actually performed. Red-check: deleting the
top-up call while keeping the counter turns the recovery test RED — the counter cannot stay
truthful after the code it describes is removed.

Call budget, asserted by spy rather than by reading source: 2 on default and single-layer,
`≤ 2 + 2L` on strict subsets. A negative control confirms zero extra calls and
`fired: false` when `recall_active_only` is off.

**Fence intact** (this fix was gated on an explicit amend hop, ruled ALLOW): no `bm25_search`
parameter or SQL change, no new public storage method, no SQL status predicate. `git diff` on
`storage/relational.py` is empty.

The pre-fix starvation is preserved as a strict-xfail characterisation node: if starvation ever
returns, it XPASSes and fails the suite.
